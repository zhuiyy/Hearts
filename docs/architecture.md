# 代码阅读指南

项目围绕游戏规则、玩家交互和可复现实验组织代码。
以下按数据定义、状态转换、对局编排和统计评估的顺序介绍各模块。

## 1. `cards.py`、`types.py`：约定语言

- `Card` 是不可变值对象。花色依次为梅花、方块、黑桃、红心；点数为 2–14。
- `Card.id = suit * 13 + rank - 2`，范围 0–51，是序列化和特征编码共用的牌编号。
- `PassAction` 表示一次选择三张牌，`PlayAction` 表示出一张牌。
- `Play` 是一条公开出牌；`Trick` 保存完整的一墩、赢家与罚分。
- `Observation` 只包含自己的手牌、自己的换牌信息及 `PublicState`。
- `PublicState.raw_scores` 是本副已经结算的原始罚分；`HandResult.scores` 是射月处理后的结算。
- `match_scores` 始终是本副开始前的累计分，不混入尚未结算的一副。

外部数据使用冻结的 `dataclass(slots=True)`、元组与枚举。外部拿不到内部集合，
也不能通过修改观测来修改游戏。Python 的进程内接口隔离不等于对恶意插件的安全隔离；
未来不可信策略需要放到独立进程中。

## 2. `deal.py`、`seeds.py`：发牌与随机性

`Deal` 保存四份不可变的初始手牌，并检查每人 13 张、全副 52 张恰好出现一次。
显式保存牌局使复赛不依赖过去的随机数调用次数。

`Seeds(root).derive(*path)` 使用带版本的 SHA-256 派生整数种子。
路径包含类型信息，因此整数 `1` 和字符串 `"1"` 不相同。
`rng(*path)` 每次返回一个新的局部 `random.Random`，不会推进其他流。

命名约定：

| 用途 | 路径示例 |
|---|---|
| 比赛发牌 | `("match", "deal", hand_number)` |
| 比赛玩家 | `("match", hand_number, "agent", seat)` |
| 评估发牌 | `("evaluation", split, "deal", block)` |
| 评估玩家 | `("evaluation", split, block, direction, rotation, "agent", seat)` |
| 训练流约定 | `("training", run_id, ...)`，与测试流分别派生 |

`AgentContext` 只给玩家自己的种子，不给 root seed、发牌种子和其他玩家种子。
策略作者应在实例内部创建自己的 RNG；使用 NumPy / PyTorch 时也应显式初始化各自的生成器。
回放保存实际初始牌局与全部动作，因此验证回放不依赖 shuffle 算法。
复现实验应固定 Python 与依赖版本，以控制不同版本随机算法的差异。

## 3. `rules.py`、`engine.py`：唯一规则实现

`rules.py` 只做纯计算：合法出牌、一墩结算、一副结算。
`HeartsHand` 是唯一会改变牌局状态的地方，生命周期如下：

```text
PASSING --四人提交并统一交换--> PLAYING --13 墩--> FINISHED
KEEP --------------------------------> PLAYING
```

`submit(player_id, action)` 先验证阶段、座位、动作类型和合法性，然后改变状态。
非法动作抛出 `IllegalAction`，不改变状态、不记录动作、不代打。

换牌按 0–3 号位收集，但提交期间四人的手牌始终保持原样。
第四人提交后才统一移除和接收。观测不会暴露别人的待结算选择。

内部手牌使用 `set[Card]`：成员判断和删除是平均常数时间。
观测时最多对 13 张牌排序，得到稳定的展示和选择顺序。
桌面最多 4 张，完成历史最多 13 墩，使用列表保存；接口处转为元组快照。
手牌、当前墩和完成的墩分别记录牌的归属，规则引擎使用普通 Python 数据结构。
动作记录用于审计，不参与判定规则；公开历史的规则语义来自完成的墩与当前桌面。

集合直接表达持有的牌，便于检查成员关系和出牌操作。
高吞吐采样的存储优化应以性能测量为依据，并保持观测和动作协议稳定。

## 4. `agents.py`、`arena.py`：连接玩家

唯一的策略方法是 `act(observation) -> PassAction | PlayAction`。
`AgentSpec` 包含名称和创建函数，用于配置每个座位的玩家。
`run_hand` 为每个座位创建独立实例，每副重建，避免记忆跨玩家或跨副泄漏。
策略需要使用累计比赛上下文时，可从公开的 `match_scores` 读取。

`run_hand` 只负责询问当前玩家并调用 `submit`；它不实现发牌、合法性或计分。
`run_match` 只负责下一副、累计分与 100 分结束条件。训练、网页和终端不应该另写规则循环。

`terminal.py` 将终端输入转换为统一的玩家动作。
每个座位通过 `AgentSpec` 独立配置，人工输入和自动策略使用相同的观测与动作接口。

## 5. `replay.py`：完整审计

完整回放只能在结束后导出，包含初始手牌、换牌与出牌、规则版本和结算。
这是有特权的数据，不能传给正在对局的策略或普通网页客户端。
`initial_deal`、`action_records` 也只供可信编排器使用。

回放重新创建 `HeartsHand` 并逐条调用同一个 `submit`，最终核对分数。
不合法、未完成、版本错误或结算不一致的回放会失败。
保存文件使用独占创建，不会覆盖旧实验。

网页按以下边界接入：公开页面只序列化 `PublicState`；玩家页面只序列化该座位的
`Observation`；动作仍交给引擎验证；完整回放只在结束后开放。
事件视图可从当前桌面、完成的墩与状态变化生成，前端不重新计算规则。

## 6. `evaluation.py`、`statistics.py`：实验与推断

一个独立 block 是一副初始牌。在该牌上分别运行四种换牌方向、四个焦点座位，
得到 16 个试验。每个试验分别运行 baseline 与 candidate，共 32 副完整模拟。
三名对手相对焦点玩家的位置不变，整个阵容轮换。

两组的初始牌、对手、座位和玩家随机种子相同；策略动作变化不会改变后续发牌。
每次模拟都重新创建策略，避免前一组或前一轮的记忆影响下一组。
对手的路径发生分歧后，它们消耗随机数的次数可能不同；相同初始流不代表每一步动作耦合，
但不影响两组边际分布，也不会影响独立发牌流。

罚分越低越好。第 b 个 block 的差异为：

\[
D_b=\frac{1}{16}\sum_{d=0}^{3}\sum_{s=0}^{3}
\left(S^{\mathrm{baseline}}_{b,d,s}-S^{\mathrm{candidate}}_{b,d,s}\right).
\]

双侧配对 t 检验等价于对独立的 block 差异做单样本检验：

\[
\bar D=\frac{1}{B}\sum_{b=1}^{B}D_b,\qquad
s_D^2=\frac{1}{B-1}\sum_{b=1}^{B}(D_b-\bar D)^2,
\]

\[
\operatorname{SE}(\bar D)=\frac{s_D}{\sqrt B},\qquad
t=\frac{\bar D}{s_D/\sqrt B},\qquad \mathrm{df}=B-1.
\]

实现委托 SciPy 计算双侧 p 值及 t 置信区间；少于两个 block、非有限数或样本方差为零时拒绝检验。
同一副牌上的 16 个试验不能当作 16 个独立样本。小样本且分布非正态时 t 推断可能失准；
可使用以 block 为单位的 bootstrap 做敏感性分析。

`holm_adjust` 对一组预先确定的比较统一做 Holm 多重检验校正；t 置信区间描述单次比较的均值，
多个区间的同时覆盖率需要单独控制。
校正不处理反复查看结果后停止、多轮调参选优或多个训练种子的层级变异。
这些要通过实验设计、独立最终测试及分层分析处理。

结果只针对指定的三个对手配置与单副罚分目标，不表示全局最强，也不自动等价于整场胜率。
